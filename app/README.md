# Демка трёхступенчатой загрузки изображений

SSR-приложение на Nuxt 4: сервис принимает изображения в высоком качестве, режет
размеры, делает плейсхолдер и отдаёт карточку товара, которая видна мгновенно.

## Запуск

```bash
pnpm install
pnpm dev          # http://localhost:3010
```

Данные (объекты и записи) лежат в `.data/` и в git не попадают. Чтобы начать
с чистого листа — удалить каталог и перезапустить сервер.

> Сервер слушает **только IPv6**, поэтому `localhost:3010` работает,
> а `127.0.0.1:3010` — нет.

## Как устроен плейсхолдер

Плейсхолдер лежит **отдельным слоем** (псевдоэлемент рамки), а не фоном на самом `<img>`.
Причина: браузер растягивает 20 пикселей примерно в десять раз билинейной интерполяцией,
а она сглаживает только соседние пиксели и даёт **мягкие квадраты, а не размытие** —
картинка выглядит просто плохой. Настоящий блюр даёт `filter: blur()`, но повесить его
на `<img>` нельзя: он размоет и загруженную картинку. Псевдоэлемент решает обе задачи —
лишнего *тега* в разметке не появляется, `<img>` сохраняет `alt` и `srcset`.

Подмена плавная: сначала картинка проявляется поверх размытого слоя (0,45 с), и только
став непрозрачной — слой гаснет (0,3 с). Одновременное гашение дало бы вспышку.
Анимация включается **только на клиенте**: иначе без JS изображения остались бы
невидимыми, а файлы из кеша выстреливают `load` до гидратации.

## Три ступени

| Ступень | Что показывается | Откуда берётся | Цена |
|---|---|---|---|
| **1** | размытый плейсхолдер | инлайн в HTML, атрибут `style` | ~200–340 B, **ноль запросов** |
| **2** | карточная копия 300 px | `/cdn/<sha>/300.webp` по сети | ~3–13 КБ |
| **3** | полный размер | подключается при открытии карточки | ~62 КБ |

Ступень 1 рисуется первым пейнтом, до любого сетевого запроса за картинками.
Ступень 3 в каталоге не грузится вовсе.

## API

### `POST /api/images`

`multipart/form-data`, поле `file` (можно несколько). Query: `?sizes=300,640,1280`.

```bash
curl -X POST "http://localhost:3010/api/images?sizes=300,640,1280" \
  -F "file=@photo.jpg" -F "file=@photo2.jpg"
```

Ответ — запись с готовым плейсхолдером (уже с префиксом) и ссылками на CDN:

```json
{
  "id": "aa601686-…",
  "width": 1200, "height": 1697,
  "placeholder": "data:image/webp;base64,UklGRk…",
  "srcset": "/cdn/<sha>/300.webp 300w, /cdn/<sha>/640.webp 640w, …",
  "variants": [{ "width": 300, "height": 424, "bytes": 12943, "url": "/cdn/…/300.webp" }],
  "timings": { "probe": 2.9, "variants": 137.7, "placeholder": 1.9 }
}
```

### `GET /api/images/:id` · `GET /api/images` · `GET /cdn/<ключ>`

У `/cdn/**` есть отладочный `?delay=<мс>` — притормаживает отдачу, чтобы увидеть
ступени. Замедленные ответы отдаются с `no-store`: иначе `?delay=` попал бы
в ключ кеша и «медленный» URL после первого запроса стал бы мгновенным.

## Конвейер обработки

```
оригинал ──┬─→ 300 px WebP ──→ 20 px WebP → base64 → в БД
           ├─→ 640 px WebP
           └─→ 1200 px WebP        (в объектное хранилище)
```

Видимые размеры режутся **каждый из оригинала** — иначе накапливаются
поколенческие потери. Плейсхолдер — исключение: он делается из самой мелкой
копии, потому что на 20 пикселях предыдущее сжатие неразличимо, а замер
показывает выигрыш вчетверо (**1,9 мс** против 10 мс из оригинала).

Прочие правила:

- **Апскейла нет.** Запрос шире оригинала прижимается к оригиналу, но не
  отбрасывается: иначе на снимке 1200 px запрос `300,640,1280` дал бы только две
  копии, и самой крупной ступени не осталось бы.
- **Дедупликация по sha256** содержимого. Повторная загрузка того же файла
  не создаёт запись и не запускает обработку.
- **Тип определяется по содержимому**, а не по расширению или заявленному MIME.
- **EXIF-ориентация применяется к пикселям** до сохранения, метаданные вырезаются.

## Что где лежит

```
server/utils/storage.ts   S3-совместимый интерфейс + драйвер файловой системы
server/utils/pipeline.ts  обработка: размеры, плейсхолдер, тайминги
server/utils/db.ts        репозиторий записей (JSON; схема для PostgreSQL — в ../docs/ARCHITECTURE.md)
server/api/images/        загрузка и выдача
server/routes/cdn/        отдача объектов
app/components/SmartImage.vue   компонент трёх ступеней
app/pages/index.vue       каталог (ступени 1–2)
app/pages/product/[id].vue карточка товара (ступень 3)
app/pages/why.vue         исследования: скорость → бизнес-показатели
```

## Почему хранилище названо `useObjectStorage`, а не `useStorage`

`useStorage` — встроенный в Nitro доступ к его KV-слою. Одноимённый авто-импорт
молча перекрывает фреймворковый, и это выясняется в тот момент, когда он реально
понадобится.

## Ограничения демки

- Записи в JSON-файле, не в БД. Вставки сериализованы через очередь и пишутся
  атомарным переименованием, но настоящих транзакций нет.
- Обработка синхронная. Так можно, пока считаем только WebP: полный конвейер
  укладывается в сотни миллисекунд. С добавлением AVIF (≈2 с на копию) понадобится
  очередь — разделение описано в `../docs/ARCHITECTURE.md`.
- Хранилище — файловая система. Интерфейс `ObjectStorage` рассчитан на подмену
  драйвера на S3/MinIO без правок в конвейере и API.
