# Сервис изображений — схема

> Статус: **проект схемы, не реализация.** Записано по итогам замеров в этом репозитории.
> Ничего из описанного ниже пока не построено.

Продукт: сервис, который принимает изображения пачками, кладёт оригинал в S3, сжимает
с минимальными потерями (задача уровня TinyPNG) и отдаёт потребителю готовый набор
размеров плюс плейсхолдер, который рисуется первым пейнтом.

---

## 1. Что уже измерено и на чём стоит схема

Замеры sharp на снимке 1200×1697, Node 26, Apple Silicon:

| Операция | Время | Вывод |
|---|---:|---|
| метаданные (width/height) | 0,3 мс | синхронно |
| **плейсхолдер 20 px → WebP** | **10 мс** | **синхронно** |
| производная 320 px WebP | 31 мс | асинхронно |
| производная 1280 px WebP | 231 мс | асинхронно |
| производная 1280 px AVIF | 1991 мс | асинхронно |

**AVIF дороже плейсхолдера в ~200 раз.** Отсюда единственная важная граница в системе:
плейсхолдер успевает посчитаться внутри HTTP-запроса загрузки, тяжёлые производные — нет.

Второй замер: браузерный `canvas.toDataURL('image/webp')` даёт файл **втрое тяжелее**, чем
sharp при том же качестве (≈1 КБ против 335 B). Следствие для API: **клиент не присылает
готовый плейсхолдер**, он только предпросматривает. Кодирует сервер.

## 2. Поток загрузки

```
                     ┌──────────────────────────────────────────┐
   POST /v1/images   │  СИНХРОННО — в том же запросе, ~15 мс    │
   (multipart)  ───► │                                          │
                     │  1. Валидация типа по сигнатуре файла    │
                     │     (не по расширению и не по MIME)      │
                     │  2. sha256 содержимого → ключ объекта    │
                     │     дубликат? → возвращаем существующий  │
                     │  3. Оригинал → S3 (originals/<sha>)      │
                     │  4. sharp: метаданные + плейсхолдер      │
                     │  5. ОДНА транзакция в БД:                │
                     │     image + placeholder                  │
                     │  6. 201 + id, запись уже рендерится      │
                     └───────────────────┬──────────────────────┘
                                         │ enqueue
                                         ▼
                     ┌──────────────────────────────────────────┐
                     │  АСИНХРОННО — воркеры, секунды           │
                     │                                          │
                     │  7. Производные: 320/640/1280/2560       │
                     │     × WebP и AVIF                        │
                     │  8. Строки в image_variant + пометка     │
                     │     variants_ready = true                │
                     └──────────────────────────────────────────┘
```

**Идемпотентность.** Ключ объекта — sha256 содержимого. Повторная загрузка того же файла
не создаёт новый объект и не запускает воркеров заново. Для пакетной загрузки это главное:
клиент может ретраить пачку целиком, не боясь размножить данные.

**Пока производные не готовы — отдаём оригинал.** Страница, которая ждёт воркера, хуже
страницы, которая отдала файл потяжелее. Плейсхолдер при этом уже есть с первой секунды.

## 3. Модель данных

Оригинал — в S3. **Плейсхолдер — в БД**, строкой, рядом с записью: он нужен на каждый рендер,
и ходить за ним в объектное хранилище бессмысленно.

```sql
CREATE TABLE image (
  id              uuid PRIMARY KEY,
  sha256          bytea NOT NULL UNIQUE,   -- идемпотентность и дедупликация
  storage_key     text  NOT NULL,          -- originals/<sha>
  mime            text  NOT NULL,
  width           int   NOT NULL,          -- без них будет CLS
  height          int   NOT NULL,
  bytes           bigint NOT NULL,

  -- плейсхолдеры: считаются один раз при загрузке
  lqip_webp       text  NOT NULL,          -- data URI, ~300 B — основной
  lqip_int        int   NOT NULL,          -- «одно число», 6 B — для длинных списков
  dominant_hex    char(7) NOT NULL,        -- запасной вариант

  variants_ready  boolean NOT NULL DEFAULT false,
  created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE image_variant (
  image_id  uuid NOT NULL REFERENCES image(id) ON DELETE CASCADE,
  width     int  NOT NULL,
  format    text NOT NULL,                 -- 'webp' | 'avif'
  storage_key text NOT NULL,
  bytes     bigint NOT NULL,
  PRIMARY KEY (image_id, width, format)
);
```

**Три плейсхолдера, а не один** — потому что у них разные ниши, и это уже посчитано:
`lqip_webp` (~335 B) для первого экрана, `lqip_int` (6 B) для длинных списков, где сотня
карточек по 335 B добавила бы 33 КБ в документ, `dominant_hex` как запасной путь.

**Инвариант, который ломается чаще всего:** `storage_key` и `lqip_webp` пишутся **одной
транзакцией**. Иначе гонка — страница успеет отрендерить запись, у которой картинка есть,
а плейсхолдера ещё нет, и эффект пропадёт ровно на свежезагруженных записях.

## 4. Image sets — отдача потребителю

Запись отдаётся одним объектом, из которого потребитель собирает и `<img>`, и фон.

```json
{
  "id": "…",
  "width": 1200,
  "height": 1697,
  "placeholder": "data:image/webp;base64,…",
  "lqip": 441323,
  "color": "#af9a95",
  "src": "https://cdn/…/1280.webp",
  "srcset": "…/320.webp 320w, …/640.webp 640w, …/1280.webp 1280w"
}
```

### Основной вариант: `<img>` с плейсхолдером в `style`

**Плейсхолдер и `srcset` не конкурируют** — это разные роли. `srcset` перечисляет настоящие
файлы, из которых браузер выбирает один под экран; плейсхолдер показывает то, что видно,
пока выбранный файл едет. Они прекрасно живут в одном теге:

```html
<img src="…/1280.webp"
     srcset="…/320.webp 320w, …/640.webp 640w, …/1280.webp 1280w, …/2560.webp 2560w"
     sizes="(max-width: 700px) 100vw, 640px"
     width="1200" height="1697"
     alt="Осмысленное описание"
     decoding="async"
     style="background-image:url('data:image/webp;base64,…');background-size:cover">
```

**SEO при этом не страдает вообще.** Тег остаётся настоящим `<img>` с `src`, `srcset` и `alt` —
всё, что индексирует поиск по картинкам, на месте. `style` для индексации это просто оформление.

Вписывать data-URI в сам `srcset` **нельзя** — технически он туда пролезет, но браузер возьмёт
его как окончательную картинку и на узком экране навсегда покажет размытое пятно.

### Когда фон — и чего это стоит

Регресс по SEO даёт не плейсхолдер, а **подмена тега**: если контент показывать как
`<div style="background-image:url(photo.webp)">`, то нет ни `alt`, ни `srcset`, и поиск
по картинкам такое не индексирует. Плюс придётся руками описывать выбор размеров через
`image-set()` или медиазапросы.

Правило: **фоном может быть только плейсхолдер, но никогда — сам контент.** Для декоративных
блоков (обложки, баннеры-плитки), которые и не должны индексироваться, фон допустим.
API отдаёт данные, которых хватает на оба случая; решение принимает потребитель.

### Две ловушки

- **Прозрачность.** У PNG с альфа-каналом фон просвечивает сквозь прозрачные места и после
  загрузки. Либо не ставить плейсхолдер, либо снимать его по событию `load`.
- **`object-fit`.** При `object-fit: contain` содержимое займёт не всю рамку, а фон растянут
  на всю — по краям останется размытая полоса. `background-size` держать согласованным.

## 5. Сжатие «как TinyPNG»

TinyPNG — это не один алгоритм, а связка: квантование палитры для PNG плюс перекодирование
в современный формат. Практическая замена целиком закрывается sharp:

| Вход | Что делать | Ожидаемая экономия |
|---|---|---|
| PNG (скриншоты, графика) | квантование палитры + `palette: true` | 60–80 % |
| PNG/JPEG (фото) | перекодировать в WebP q75–80 | 50–70 % |
| Всё | дополнительно AVIF q50 как первый вариант в `<picture>` | ещё 20–30 % к WebP |

Три правила, без которых «минимальные потери» не получаются:

1. **Не перекодировать уже сжатое повторно.** Каждый цикл lossy → lossy теряет качество
   безвозвратно. Производные всегда считаются **из оригинала**, никогда из другой производной.
2. **Не увеличивать.** Если запрошенный размер больше исходного — отдаём исходный.
   Апскейл раздувает вес и не добавляет ни пикселя информации.
3. **Проверять, что стало легче.** Мелкая графика в AVIF бывает тяжелее исходного PNG —
   заголовок контейнера съедает выигрыш. Если производная больше оригинала, она не нужна;
   в этом же репозитории AVIF на 20 px проиграл WebP почти вдвое.

Метаданные (EXIF, GPS) вырезаются всегда, кроме ориентации — её надо применить к пикселям
до сохранения, иначе часть клиентов покажет снимок повёрнутым.

## 6. Что осталось решить

- **Хранение плейсхолдера в БД против S3.** Схема выше кладёт его в колонку. При миллионах
  записей стоит замерить, как это влияет на размер строки и на планы запросов.
- **Синхронная или ленивая генерация производных.** Очередь против генерации по первому
  запросу с кешированием на CDN. Второй вариант дешевле на холодных изображениях,
  которые никто не откроет.
- **Кто владеет CDN-инвалидацией** при перезаливке изображения с тем же id.
- **Лимиты пакетной загрузки** — сколько файлов за запрос, и что возвращать, если часть
  пачки не прошла валидацию.
