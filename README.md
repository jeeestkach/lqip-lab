# image-placeholder-compare

Сравнение техник blur-плейсхолдеров для изображений в SSR-приложении: что именно
увидит клиент, пока грузится картинка, и сколько байт каждая техника добавляет в HTML.

Всё считается локально настоящими библиотеками (`sharp`, `thumbhash`, `blurhash`) —
цифры на странице измерены, а не взяты из статей.

## Запуск

```bash
pnpm install
pnpm build     # считает плейсхолдеры и собирает dist/index.html
pnpm open      # открыть результат в браузере
```

Свои изображения — положить в `input/` и пересобрать. Файл `main.webp`
показывается как основной пример, остальные попадают в раздел «На других изображениях».

## Структура страницы

**Блок 1 — «Как выглядит блюр».** Статичные карточки: ровно то, что видит клиент,
пока картинка ещё не пришла. Оригинал слева для сверки.

**Блок 2 — «Симуляция загрузки».** Поверх плейсхолдера проявляется оригинал.
Задержка не выдумана: считается из настоящего веса файла и выбранной скорости
(время передачи + сетевая задержка). Три пресета — канонические профили троттлинга
Chrome DevTools, так что результат можно перепроверить на вкладке Network:

| Пресет | Канал | Задержка | Для файла 79 КБ |
|---|---|---|---|
| Мобильный интернет *(по умолчанию)* | 3G, 400 Кбит/с | 400 мс | ≈ 2,0 с |
| Стандартный мобильный | 4G, 1,6 Мбит/с | 150 мс | ≈ 555 мс |
| Быстрый интернет | 50 Мбит/с | 20 мс | ≈ 33 мс |

Первая карточка блока 2 — эталон **без плейсхолдера вообще**; сравнивать надо именно с ней.

Замер оптимистичный: здесь одна картинка получает весь канал целиком, а на настоящей
странице она стоит в очереди за CSS, шрифтами, скриптами и другими изображениями.

## Что сравнивается

| Техника | Нужен JS | Суть |
|---|---|---|
| Доминирующий цвет | нет | один `#hex`, нижняя граница качества |
| Одно число (CSS-only) | нет | 20 бит в `--lqip`, декод целиком в CSS (метод Lean Rada) |
| CSS-градиенты | нет | стопка `radial-gradient` из сетки 4×4 (подход plaiceholder `.css`) |
| SVG-сетка | нет | сетка `<rect>` под `feGaussianBlur` (подход plaiceholder `.svg`) |
| base64 LQIP | нет | копия 16–24 px в WebP как data URI |
| ThumbHash | да | 21 B хэш → декод → картинка |
| BlurHash | да | 36 симв. → декод → картинка |

## Главные выводы

1. **В байтах разметки base64 LQIP и хэши идут вровень.** После честного пересжатия
   декода в WebP хэши дают ~175 B, а LQIP на 12 px — ~195 B. Спорить тут не о чем.
2. **Библиотеки хэшей отдают декод в PNG** (4–5 КБ). Сравнивать это с WebP-плейсхолдером
   некорректно — это сравнение кодеков, а не техник. В отчёте оба числа.
3. **Выбор решается эксплуатацией, а не весом.** LQIP нужен только `sharp` один раз при
   загрузке файла. Хэшу нужна библиотека на обоих концах и шаг декодирования — зато
   в БД, JSON API и мобильном клиенте он занимает 21 B вместо ~200 B.
4. **CSS-градиенты и SVG не экономят**: 1.5 КБ и 2.8 КБ против 335 B у base64 LQIP,
   при худшей детализации. Их ниша — отсутствие растрового кодека и плавный масштаб.
5. **«Одно число» — единственный настоящий минимум** (6 B), но сетка 3×2 очень грубая
   и нужны современные браузеры.

## Отклонение от спецификации «одного числа»

У Lean Rada оси цветности кодируются в диапазоне ±0.35 — он рассчитан на насыщенные цвета.
У *среднего* цвета фотографии цветность почти всегда мала: замеры на реальных снимках дают
|a|, |b| ≈ 0.01…0.08, а шаг квантования при ±0.35 равен 0.0875. Весь цвет умещается внутри
одного шага, и плейсхолдер схлопывается в нейтрально-серый.

Здесь диапазон сужен до **±0.12** (шаг 0.03) одновременно в кодере и в CSS-декодере —
они генерируются из одной константы `C_HALF` в `src/strategies/lqip-int.mjs`, поэтому всегда
согласованы. Плата: такой CSS несовместим с чужим, написанным под исходный диапазон.

## Структура

```
input/                  исходные изображения (main.webp — основной пример)
src/generate.mjs        точка входа: считает всё и пишет dist/
src/render.mjs          сборка HTML
src/oklab.mjs           преобразования sRGB ↔ Oklab
src/strategies/         по файлу на семейство техник
dist/index.html         результат
```
