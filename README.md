# lqip-lab

Что показывать пользователю, пока грузится картинка. Исследование техник
blur-плейсхолдеров с настоящими замерами — и рабочая SSR-демка сервиса изображений,
который эти плейсхолдеры отдаёт прямо в HTML.

Все цифры здесь **измерены**, а не взяты из статей: считают `sharp`, `thumbhash`
и `blurhash`, а страница собирается из результатов замера.

## Две части

| Каталог | Что это |
|---|---|
| `src/` → `dist/index.html` | **Исследование.** Семь техник плейсхолдеров на одном изображении: вес, детальность, нужен ли JS. Плюс интерактив — можно бросить свои файлы и посмотреть, во что они превратятся. |
| `app/` | **SSR-демка** на Nuxt 4: загрузка изображений, конвейер обработки, каталог, карточка товара и A/B-сравнение стратегий рендера под симуляцией медленного канала. |
| `docs/ARCHITECTURE.md` | Схема сервиса: поток загрузки, DDL таблиц, image sets, сжатие уровня TinyPNG, открытые вопросы. |

```bash
# исследование
pnpm install && pnpm build && pnpm open

# демка
cd app && pnpm install && pnpm dev     # http://localhost:3010
```

> Nuxt слушает **только IPv6**: `localhost:3010` работает, `127.0.0.1:3010` — нет.

## Что выяснилось

**В байтах разметки base64 LQIP и хэши идут вровень.** После честного пересжатия
декода в WebP ThumbHash даёт 175 B, BlurHash 171 B, а base64 LQIP на 12 px — 195 B.
Спорить не о чем. Библиотеки хэшей отдают декод в **PNG** (4–5 КБ), и сравнивать его
с WebP-плейсхолдером — это сравнение кодеков, а не техник.

**Выбор решается эксплуатацией, а не весом.** LQIP нужен только `sharp` один раз
при загрузке файла. Хэшу нужна библиотека на обоих концах и шаг декодирования —
зато в БД, JSON API и мобильном клиенте он занимает 21 B вместо ~200 B.

**Браузерный кодировщик втрое хуже серверного.** `canvas.toDataURL('image/webp')`
даёт ~1 КБ там, где `sharp` при том же качестве даёт 335 B. Значит «посчитать
плейсхолдер на клиенте и прислать готовым» — плохая идея.

**Плейсхолдер нельзя класть фоном на сам `<img>`.** Браузер растягивает 20 пикселей
примерно в десять раз билинейной интерполяцией, а она сглаживает только соседние
пиксели и даёт **мягкие квадраты, а не размытие**. Настоящий блюр даёт `filter`,
но на `<img>` его вешать нельзя — размоет и загруженную картинку. Решение —
псевдоэлемент рамки: лишнего *тега* не появляется, `<img>` сохраняет `alt` и `srcset`.

**Плейсхолдер и `srcset` не конкурируют.** `srcset` выбирает ровно один вариант
и показывает только его — это механизм выбора разрешения, в нём нет измерения «время».
Нужны два слоя, а не два кандидата. SEO при этом не страдает: тег остаётся
настоящим `<img>` со всеми атрибутами.

**Граница синхронного и асинхронного задаётся замером.** Плейсхолдер 20 px — 10 мс,
производная 1280 px в AVIF — 1991 мс, в 200 раз дороже. Плейсхолдер обязан считаться
внутри запроса загрузки, тяжёлые производные — только очередью.

## Отклонение от спецификации «одного числа»

У [Lean Rada](https://leanrada.com/notes/css-only-lqip/) оси цветности кодируются
в диапазоне ±0.35 — он рассчитан на насыщенные цвета. Но у *среднего* цвета фотографии
цветность почти всегда мала: замеры дают |a|, |b| ≈ 0.01…0.08, а шаг квантования
при ±0.35 равен 0.0875. Весь цвет умещается внутри одного шага, и плейсхолдер
схлопывается в нейтрально-серый.

Здесь диапазон сужен до **±0.12** (шаг 0.03) одновременно в кодере и в CSS-декодере —
они генерируются из одной константы `C_HALF` в `src/lqip-format.mjs`, поэтому всегда
согласованы. Плата: такой CSS несовместим с чужим, написанным под исходный диапазон.

## Симуляция загрузки

Демка не использует фиксированную задержку: она даёт всем файлам одинаковую паузу,
а в жизни время зависит от веса файла и от того, что канал делится между параллельными
загрузками. Модель воспроизводит это — шесть соединений к источнику, каждое со своей
долей полосы, файл грузится `вес / доля + задержка`. Карточки появляются неровными
пачками сами собой, как на настоящем каталоге.

Профили — канонические из троттлинга Chrome DevTools (3G 400 Кбит/с, Slow 4G
1,6 Мбит/с, Fast 4G 9 Мбит/с, Wi-Fi 50 Мбит/с). Файлы прогреваются в кеш перед
прогоном, поэтому замер точен и повторяем.

## Происхождение изображений

- `input/03–06.jpg` — picsum.photos, **Unsplash License**, свободное использование.
- `input/main.webp`, `input/provybor/*.webp` — товарные снимки с `cdn.provybor.com`,
  взятые владельцем репозитория с собственной площадки. Они отдаются публично
  и без авторизации, но **права на конкретные товарные фотографии могут принадлежать
  поставщикам-мерчантам**, а не платформе. Файлы лежат здесь только как реалистичный
  набор для замеров.

Если форкаете — замените их своими: код от набора не зависит, достаточно положить
любые изображения в `input/` и пересобрать.
